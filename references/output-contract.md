# 统一输出契约

全部正式产物使用契约 `2.0.0`。JSON 顶层包含：`schema_name`、`schema_version`、`generated_at`、`case_reference`、`report_type`、`workflow_stage`、`report_status`、`participant_reference`、`target_event`、`executive_summary`、`received_information`、`verified_facts`、`unverified_information`、`derived_results`、`recommendations`、`scenario_switches`、`safety`、`next_actions`、`evaluation_boundary`、`privacy` 与 `provenance`。

`null` 仅表示未知值，`[]` 仅表示无项目。区分：`unverified`、`confirmed_absent`、`source_blocked`、`not_allowed`、`insufficient_evidence`。

面向跑者的 Markdown 默认中文，稳定报告标题为 `越野跑规划资料确认`、`越野跑规划准备报告`、`比赛策略与情景规划`、`比赛中状态更新`、`赛后复盘`。结论置前；红旗时 `安全停止` 置前。机器状态、哈希、来源和隐私细节放入 `技术附录`。

面向普通读者（非程序员）的报告，正文禁止出现英文围栏代码块（raw JSON / YAML / GPX / SQL / 脚本 / 数据 dumps 等）；机器可读数据（哈希、schema、来源 URL、年份、解析结果）仅可放入 `技术附录`，且以说明性文字呈现，不用代码块包装。越野跑专业术语照常保留（如累计爬升、递加、CP、关门、ITRA、组别代码 50KM 等），无需为术语额外附加通俗化解释。少量必要标识符（ITRA ID、组别代码、赛事实体名）可作行内数据保留，但不得用代码块包装。默认中文为硬性默认，仅当请求显式要求“英文输出”时可整体切换语言。

普通报告不得包含全名、完整 ITRA ID 或行级历史。赛道/CP/关门证据未核验时，不得产出个人完赛预测或精确 CP 计时。`user_facing_prediction_allowed=false` 时，仍可在 CP 证据齐全、非红色安全停止且输入/假设公开说明的前提下，输出标注为“条件式执行预算（非官方、非已验证个人预测）”的到站、站停、离站、累计、关门余量和完成窗口；不得把该预算称作已验证预测。

`完整CP策略报告` 默认是证据门槛报告类型：每行必须有至少一个中间 CP 的目标年份/精确组别官方 CP 证据，即官方结构化 CP 表/官方 GPX，或绑定 `source_url`、`retrieved_at`、`raw_sha256`、`applicable_year`、`applicable_group`、`parser_method` 的官方赛道图/路书/PDF/图片视觉转录。仅起终点与全部 `derived` 行无效。若完整采集后仍无当年 CP 细节、但有同赛事同组别的官方历史路线，系统必须先要求用户明确确认；确认以当前 request 的不可覆盖 `historical_reference_consent.json` 记录后，允许生成 `历史路线参考版`。它必须在标题和每个 CP/补给/关门引用中标注历史届次/非当年已确认，并要求赛前复核当年公告。发现路线附件但未获取/解析，或没有上述用户确认时，唯一允许的跑者产物是 `赛道资料待补全确认单`；其 `terminal_report_allowed` 为 `false`，且不得包含 CP 到达/离站预算、余量、6.1 执行行或 6.2 逐段战术。

当年官方 CP 行在完整搜索后仍不可用时，可解析可访问的同赛事/同组官方历史路线并标为 `official_historical_reference`、显示来源年份；但绝不可将其提升为当年官方事实或当年官方关门。

`race_strategy` 必须有目标组别抓取回执，绑定赛事年份、精确组别、抓取时间、官方 URL/状态与路线/CP/关门搜索覆盖。完整章节骨架、6.1、6.2 与任何 CP 执行预算，仅在上述 CP 证据门槛通过后允许；唯一例外是已记录用户确认的 `历史路线参考版`。不得用历史成绩、网页摘要、起终点或派生行填补目标年 CP 字段。赛事细节不得写“尚未取得”：应使用 `未执行组别抓取`（硬错误）、`已抓取但尚未确认`（含抓取时间和下一动作）或 `官方明确尚未发布`（仅有同年同组官方发布证据）。

默认中文结构：结论/安全边界；赛事搜索回执；跑者/当前状态边界；估计与验证边界；条件式整体建议；`6.1 全段总览表`；`6.2 逐段战术详解`；全程规则；情景切换；来源/隐私附录。

`6.1 全段总览表` 固定基础顺序：`#`、`赛段区间`、`km`、`爬升`、`下降`、`本段耗时`、`到站停留`、`出站用时`、`累计用时`、`到达时间`、`离站时间`、`关门时间`、`余量`、`赛道难度`。起点为 S0 原点；终点与每个中间 CP 是分段终点。表后给出距离/D+/D-/移动/站停/条件完成总计。证据层级、来源年份、路线适用性、补给/装备、行动和详细风险放在 6.2 与技术产物，不增加 6.1 固定列。

当完整 CP 策略报告可交付时，6.1 的每个赛段行都必须填写上述固定列；终点的站停/离站可用 `—`，但不得用 `待补充`、空值或泛化段落替代执行预算。6.2 必须与 6.1 赛段逐一对应，每张战术卡固定包含：`数据边界`、`距离与升降`、`条件式窗口`、`赛道特征`、`风险`、`行动策略`、`补给/装备`、`关门边界`。交付前必须对实际要交付的 Markdown 运行机器校验；未通过校验不得生成 HTML/PDF。

仅当 `health_state.injury_status` 是选手明确、非空自述时，才在 `昼夜` 前追加伤痛列；可安全识别时使用报告部位标签（`膝`、`踝`、`小腿` 等），否则用 `伤痛关注`。只给观察/降级/停止建议，不诊断。缺失、`none`、未知、仅公开或推断伤情均省略整列。仅当官方起跑/关门与条件赛道窗口进入夜间时追加 `昼夜`，可显示 `☀️→🌙`；纯日赛或不入夜短赛省略整列、逐段夜间条款和夜间规则行。

逐段详解重复证据边界、地形、风险、行动、补给/装备与关门边界；只有相应可选列启用时才重复伤痛关注或夜间行动。存在可用跑者锚点与安全权限时，官方历史行可显示加宽的条件参考窗口，但其关门/余量绝非目标年官方信息。不得由公开历史推断当前健康；没有自述时使用黄色保守边界，而非伪造绿色状态。
